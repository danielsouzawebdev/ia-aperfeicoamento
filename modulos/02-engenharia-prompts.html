2. Exemplo: classificador comercial

Você atua como analista comercial da Café Horizonte. Entrada: mensagem recebida de um potencial cliente. Tarefa: classifique a mensagem em uma das categorias: LEAD_QUENTE, LEAD_MORNO, LEAD_FRIO, SUPORTE ou OUTRO. Regras: - LEAD_QUENTE: intenção explícita de compra ou pedido de orçamento. - LEAD_MORNO: interesse claro, mas sem pedido imediato. - Não invente dados ausentes. - Se houver ambiguidade relevante, use OUTRO. Saída obrigatória: { "categoria": "", "resumo": "", "proxima_acao": "", "confianca": "alta|media|baixa" }

A saída estruturada é útil quando uma automação precisa ler campos previsíveis. A API do Gemini oferece suporte a respostas estruturadas com JSON Schema; no curso, começamos simulando a lógica sem exigir código.

3. Prompt para pessoa x prompt para sistema

Conversa humana

Uma resposta elegante pode ser suficiente.

Analise este lead e diga o que você acha.

Entrada de workflow

O sistema precisa de campos previsíveis.

Classifique o lead e retorne somente JSON com: categoria, urgencia, resumo e proxima_acao.

Regra: quando outra etapa do workflow vai consumir a resposta, prefira formato estruturado e critérios explícitos.

4. Few-shot: ensinar pelo exemplo

Quando categorias podem ser interpretadas de maneiras diferentes, exemplos ajudam a fixar o padrão desejado.

Classifique mensagens em LEAD_QUENTE, LEAD_MORNO ou SUPORTE. Exemplo 1: Entrada: "Quero contratar hoje. Pode me enviar o link?" Saída: {"categoria":"LEAD_QUENTE","motivo":"intenção imediata de compra"} Exemplo 2: Entrada: "Meu pedido chegou com item faltando." Saída: {"categoria":"SUPORTE","motivo":"problema pós-venda"} Agora classifique: "Estou comparando planos e gostaria de entender os preços."

⚠️ Prompt robusto também prevê falha

Não escreva apenas o caminho feliz. Defina o que fazer quando faltarem dados, quando a mensagem estiver ambígua e quando a resposta não puder ser determinada com segurança.

Se não houver informação suficiente para classificar, use categoria "REVISAR" e explique qual dado está faltando. Não invente informações.

💡 Analogia: prompt de produção é um contrato, não um pedido informal

Em uma conversa humana, “me ajuda com isso” pode funcionar porque a outra pessoa pergunta, interpreta e negocia o significado. Em um workflow, a próxima etapa espera campos, categorias e regras previsíveis. Por isso, um prompt de produção se aproxima de um contrato de interface: define o que entra, o que deve acontecer, o que é proibido e o que deve sair.

🔎 Instrução, dado e regra: mantenha as camadas separadas

Instrução

O comportamento esperado. Ex.: “classifique a mensagem”.

Dado

O conteúdo variável. Ex.: a mensagem real do cliente.

Regra

Limites e critérios. Ex.: categorias permitidas e quando usar “REVISAR”.

Separar essas camadas facilita manutenção, testes e prevenção de conflitos entre conteúdo do usuário e instruções do sistema.

🧪 Teste de robustez antes de usar no workflow

  1. Teste uma entrada normal.
  2. Teste uma entrada incompleta.
  3. Teste uma entrada ambígua.
  4. Teste uma entrada fora do escopo.
  5. Teste texto que tenta modificar as regras da tarefa.
Critério: o prompt não precisa “adivinhar”. Quando faltar evidência, a saída segura pode ser REVISAR, null ou precisa_humano: true.
